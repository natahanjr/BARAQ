# Correlation Rules Policy (R001-R009)

## Design principles

- **Deterministic**: every rule is a pure predicate over group summaries
  (family, hosts, users, sources, techniques, phases) - never over alert
  titles, never probabilistic.
- **No catch-all** (spec 5.74): unrelated activity simply stays
  uncorrelated. There is deliberately no rule that accepts a bare pair.
- **Versioned**: `RULES_VERSION = "1.0.0"`; every rule carries full
  metadata (id, version, title, description, type, window, priority).
- **Windows are configurable** (spec 5.9), never hardcoded; a pair only
  correlates when it falls inside the rule's sequence window (spec 5.10),
  with a bounded 60-second clock-drift slack.

## Roster

| # | Rule | Pair predicate (earlier -> later) | Type | Window key |
|---|------|-----------------------------------|------|------------|
| R001 | Remote Access -> Execution | auth family -> exec family | TEMPORAL | authentication_to_execution (30m) |
| R002 | External Access -> Credential | auth->auth, phase IA -> CA, shared user | ENTITY | authentication_to_execution (30m) |
| R003 | Execution -> Privilege | exec family -> phase CA | TECHNIQUE_SEQUENCE | execution_to_privilege (60m) |
| R004 | Host-to-Host Lateral | no shared host, shared user/source, later phase LM | LATERAL_MOVEMENT | host_to_host_lateral_movement (60m) |
| R005 | Multi-Host Source Chain | shared source, 2+ distinct hosts | SOURCE_CHAIN | host_to_host_lateral_movement (60m) |
| R006 | User Chain Across Hosts | shared user, 2+ distinct hosts | USER_CHAIN | host_to_host_lateral_movement (60m) |
| R007 | Technique Transition | same family, same phase, different techniques | TECHNIQUE_SEQUENCE | execution_to_privilege (60m) |
| R008 | Tactic Progression | same family, different techniques, phase progression | TACTIC_SEQUENCE | multi_stage (120m) |
| R009 | Multi-Stage Sequence | chain-level: 3+ members spanning 2+ phases | MULTI_STAGE | multi_stage (120m) |

Priority is total and ordered (R001 highest); at creation the first
matching rule decides the finding type. Every matching rule's edges are
emitted (`emits_edges`: R002 -> SAME_ACCOUNT + TACTIC_TRANSITION,
R004 -> LATERAL_MOVEMENT, R007 -> TECHNIQUE_TRANSITION,
R008 -> TACTIC_TRANSITION).

## Matching rules

- A pair needs **2+ relationships** (`CORRELATION_MIN_RELATIONSHIPS`)
  before any rule is considered (spec 5.22).
- A pair must fall inside the rule's window - the TEMPORAL relationship
  is the window gate (spec 5.10). Four hours apart never correlates.
- Candidate pairs are generated by entity + time partitioning, never
  O(n^2) (spec 5.2).
- Rules evaluate group *summaries* built from the stored group record
  (family via detector map, hosts/users/sources/techniques from the
  aggregated arrays) - no alert titles, no raw events (spec 5.2).

## Chain type upgrades

The chain may resolve to a type stronger than the creating rule:

- `HOST_CHAIN` - three or more distinct hosts with a NETWORK_RELATION or
  DESTINATION_RELATION edge (documented deviation: HOST_CHAIN is a chain
  upgrade produced by `resolve_chain_type`, not a pair rule);
- `MULTI_STAGE` (R009) - 3+ members spanning 2+ tactic phases;
- `LATERAL_MOVEMENT` outranks both.

Type resolution is re-run on every extension so the finding always claims
the most specific supported hypothesis (spec 5.4).

## How to add a rule

1. Subclass `CorrelationRule` in `backend/correlation/rules/__init__.py`
   (pure predicate returning a "why" reason string or None).
2. Register the instance in `RULES` with a fresh priority.
3. Bump `RULES_VERSION`.
4. Add a pinned regression scenario in
   `tests/regression/v5-known-problems/test_correlation_known_problems.py`.
